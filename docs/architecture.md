# 架构与证据边界

`ai-asset-workflow` 是 v0.1.0-dev 工作流原型。目标是由我提出需求、Claude Code 统筹、Codex 执行生图与三维制作；我确认图片后才进入 Blender 制作。Python 标准库 CLI 已实现候选登记、审批、任务调度与结果管理。

## 职责分工

| 角色 | 工作流设计中的职责 | 当前实现与验证范围 |
| --- | --- | --- |
| 我 | 提出需求、确认风格、检查成品 | 图片批准与交付验收分别记录 |
| Claude Code | 拆解需求，统筹 Codex 与各制作工具 | 已提供控制器指引，完整串联待验证 |
| Python CLI | 登记候选、生成审阅页、管理审批及阶段任务 | 程序已实现，既有合成测试见验证记录 |
| Codex CLI | 编辑 ComfyUI 批量生图工作流，或调用 GPT Image；获批后执行三维任务 | 已实测原生图像 worker；指定后端接入与完整三维任务待验证 |
| ComfyUI / GPT Image | 按设定批量生成候选图片 | 流程设计中的两种方式；本版本没有对应适配器 |
| MCP → Blender | 连接软件，完成建模、材质与输出 | 已提供任务包，未验证完整制作与交付 |

既有记录中，Codex 原生图像 worker 已生成并登记三张候选图；图片尚未获批、不公开。实际图像模型未暴露，记录为 `null`，不能将执行代理 `gpt-6-astra` 当成图像模型。`generate-concepts` 封装已通过合成协议测试，未再次调用真实生图。Blender 制作未完成；连接情况应在执行时检查，不能沿用历史机器状态。详见 [2026-11-07 验证记录](validation.md)。本次说明同步不新增实测结果。

## 数据流

```text
可移植 brief
    │ init
    ▼
本地项目记录 ← register / ingest-concepts ← 实际图片及生成回执
    │ review                          │
    ▼                                 │ 内容哈希
review/index.html → 用户看图 → 明确批准 ┘
    │ approve：资产 ID + 候选哈希 + 用户原文
    ▼
已批准的选中参考 → packet(model) → Codex → Blender MCP
    │                                         │
    │                                  实际文件 + 阶段回执
    │                                         ▼
    │                                   model_review
    │                                         │ 检查
    └──────────────→ packet(deliver) → Codex → Blender MCP
                                              │
                                   文件校验 + 实际视觉检查
                                              ▼
                                       delivery_review
                                              │ 用户验收
                                              ▼
                                          completed
```

`generate-concepts` 默认调度 `needs_concept` 资产，显式 `--asset ID` 请求单资产变体；生成后自动导入回执。`ingest-concepts` 接入已有图像 worker 回执：图片路径相对回执目录，`approved` 保持 `false`，未暴露的图像模型标识保持 `null`。

`run-codex` 自行创建阶段任务包、执行并登记回执；`packet` 配合 `record-result` 支持外部授权执行会话，两条路径不混用任务身份或重复登记。具体回执字段以同版本任务包为准。

## 状态的含义

| 逻辑状态 | 进入依据 | 下一步 |
| --- | --- | --- |
| `needs_concept` | 项目已初始化，尚缺候选 | 生成或导入图片 |
| `generating_concept` | 图像 worker 已启动 | 等待实际结果与回执 |
| `concept_review` | 实际候选图片已登记 | 展示图片，等用户明确批准 |
| `approved` | 已记录选中候选哈希及真实批准原文 | 验证工具与范围，准备模型阶段 |
| `running` | 阶段任务已启动 | 等待结果，保持工程单写入者 |
| `model_review` | 模型阶段结果已登记 | 检查工程、结构与画面，再推进交付 |
| `delivery_review` | 交付阶段结果已登记 | 校验交付文件并供用户检查 |
| `completed` | 检查后用户验收已记录 | 交付完成；公开发布另核对授权 |
| `failed` | 某阶段失败并留下原因 | 排除原因后显式 `retry` |

表格区分业务语义；初始化、内部中间状态和具体字段以 CLI 实现为准。运行中、待审阅、完成和失败不可合并为一个“完成”标记。`retry` 只针对 `failed`，不允许用重试跳过图片批准或交付验收。

## 参考图与审批绑定

审批的对象是“这个资产的这一份图片字节”，不是主题、文件名或泛泛的风格描述。登记候选后，以内容哈希定位；`approve` 必须记录完整候选哈希和用户原文。`packet --stage model` 与 `packet --stage deliver` 都应阻止未获批的选中参考图进入执行。

哈希证明内容身份，不证明许可、质量或用户确实看过图片。控制器负责展示原图和明确指向，CLI 负责记录与约束。审批后修改、覆盖或更换图片会改变内容身份，应重新登记和审批，不能沿用旧授权。模型及交付回执需要能追溯至相应资产、阶段和获批参考。

## Blender 访问边界

- 只通过已有配置的 Blender MCP 操作本任务明确指定的新输出；不修改用户正在使用的工程，不静默改全局配置。
- 同一工程串行执行，控制器保持单写入者；是否存在进程锁须另查实现，不把调度约定宣传为已实现的锁。
- MCP 不可用时停止对应执行并报告失败，不把独立后台 Blender 当作 MCP 替代品。
- 恢复前检查残留执行和工程状态；超时、报错或进程退出后，都不能假定工程已经处于可安全继续的状态。

## 完成需要多种证据

| 检查层 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 进程与日志 | 命令执行情况、错误线索 | 资产正确或画面合格 |
| 回执与状态 | 本次阶段报告及其关联关系 | 报告内容必然真实 |
| 文件存在与内容哈希 | 产物可定位、内容身份一致 | 工程能打开、结构合理 |
| 工程检查 | 可编辑性、对象与依赖、尺度与连接 | 所有最终画面已经检查 |
| 视觉检查 | 实际查看范围内的构图、结构与细节 | 未查看画面同样合格 |
| 用户验收 | 用户接受这次交付 | 公开发布权或第三方授权 |

每一层记录已验证与未验证事项。stdout、报告文本或零退出码都不足以单独认定交付成功。

## 仓库与运行数据

公开层包含 `workflow/` CLI、`tests/`、可移植 `examples/`、文档和技能入口；`assets/cover.svg` 仅是代码绘制的文档插图。私有层使用 `runs/` 保存项目 JSON、图片、提示词、审阅页、任务包、日志、回执和制作产物。本地绝对路径只留在私有层，凭据不进入 brief 或公开文档。

外部 Skill 依赖仅通过原仓库引用：[blender-asset-pipeline](https://github.com/KKKKKennys/blender-asset-pipeline) 与 [camera-shot-library](https://github.com/KKKKKennys/camera-shot-library)。本仓库不复制其内容、不推断其许可；调用前检查任务需要和本地可用性。v0.1.0-dev 没有 ComfyUI 或图像 API 适配器。
